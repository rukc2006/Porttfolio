01

Сборщик отчётов маркетплейсов

Python · сервис по расписанию

Каждое утро в 06:00 собирает отчёты из шести кабинетов и складывает их в одну таблицу. Заменил полтора часа ручной работы: раньше отчёты выгружали руками по одному.

источник данных обработка что видит человек
Стек Python · requests · Selenium · Google Sheets API · Telegram Bot API · Планировщик задач Windows
Как устроено

Где есть API — идём в API

Ozon, Wildberries и Яндекс Маркет отдают отчёты методом. Ответ разбирается по схеме и приводится к общим колонкам.

Где API нет — поднимаем браузер

Сбер и МВидео закрыты: запускается Chrome с сохранённой сессией, отчёт скачивается как файл и читается с диска.

Повторы с уважением к Retry-After

Площадка отвечает 429 и говорит, через сколько повторить. Слепые повторы добивают квоту и блокируют ключ на час.

Решения и почему так

Ошибка громче тишины

Слетевшая сессия и недоехавший отчёт уходят в Telegram. Сбор, молча отдавший неполные данные, опаснее упавшего: по неполным цифрам принимают решения.

Обход потолка offset

Площадка не отдаёт больше 20 000 строк подряд. Запрос режется по датам, иначе хвост выгрузки теряется без единой ошибки.

02

Дашборд логистики

Python + Кофе в капсулах Nespresso «PIANO 2», 10 шт. Aurora Coffee JS · один файл

Отвечает не «сколько остатков», а что везти, куда и почему именно туда. Десять вкладок: что делать сегодня, товары, поставки, карта страны по кластерам, ЧП и потери, кластеры и склады, резервы, напоминания, журнал действий и лента новостей площадки. Действия отсортированы по деньгам на кону, потери считаются сравнением снимков за прошлые дни.

источник данных обработка что видит человек
Стек Python · Кофе в капсулах Nespresso «PIANO 2», 10 шт. Aurora Coffee JS · SVG-карта · сборка в один файл
Как устроено

Сборка отделена от показа

collect_ozon.py собирает данные и кладёт их в data.json. Сборщик подставляет его в template.html по якорю <script id="OZON_DATA">. Файл открывается без сервера.

Снимки остатков за прошлые дни

Каждый сбор сохраняет срез. Потери считаются сравнением срезов: без истории видно только «сейчас мало», а не «упало».

Карта страны по кластерам

Своя отрисовка контуров и кластеров: цвет показывает запас хода, размер — объём продаж. Подложка из сети не нужна, файл открывается на любом компьютере без интернета.

Лента новостей площадки

Новости о тарифах, коэффициентах приёмки и правилах собираются вместе с данными и раскладываются по темам: то, что меняет расчёт, помечается отдельно.

Реестр ЧП и потерь

Повреждения, пересорт и пропажи на складах ведутся списком с суммой потерь и статусом обращения — по нему видно, что уже возмещено, а что ещё висит.

Решения и почему так

«Наблюдаем» не закрывает кластер

Статус «наблюдаем» — машинная аномалия, а не происшествие. Если закрывать по нему поставки, под запрет уезжает Москва с третью выручки.

Действия отсортированы по деньгам

Не по дате и не по алфавиту. Сверху то, что нельзя откладывать, и у каждой строки написано, почему именно здесь.

05

Сайт студии танцев

Docker Compose · сервисы · репликация

Расписание занятий, преподаватели, запись клиентов. Система собрана из двух десятков контейнеров и поднимается одной командой: две базы с репликацией, три слоя сервисов, балансировка чтения, сбор логов и трассировка запроса.

источник данных обработка что видит человек
Стек Python 3.12 · FastAPI · SQLAlchemy 2 · PostgreSQL 16 · NGINX · Docker Compose · Grafana · Loki · Promtail · Jaeger · OpenTelemetry · RabbitMQ · Consul · React 19 · TypeScript · Vite · Electron
Как устроено

Чтение и запись разведены

Запись идёт только в ведущую базу, чтение — в горячую реплику. NGINX делит запросы на чтение между тремя экземплярами в пропорции 2:1:1, а запись отправляет строго туда, где открыта ведущая база.

Реплика поднимается сама

При первом запуске точка входа контейнера снимает базовую копию с ведущей и встаёт в режим горячего ожидания. Никаких ручных шагов после docker compose up.

Зеркало — отдельный контур

Через логическую репликацию поднимается вторая база со своими сервисами. На ней можно проверять изменения, не трогая тот путь, по которому ходят люди.

Логи и трассировка с самого начала

Promtail собирает логи контейнеров в Loki, дашборд Grafana показывает, какой сервис отвечает и как быстро. Запрос прослеживается через слои по идентификатору трассировки.

Решения и почему так

Три слоя вместо одного приложения

Работа с базой, правила и HTTP разведены по разным сервисам. Дороже в поддержке, но позволяет держать несколько копий каждого слоя и менять один, не задевая остальные.

Проверки готовности вместо пауз

Сервисы стартуют не по таймеру, а по готовности зависимостей: база отвечает на pg_isready, только потом поднимается слой данных. Иначе половина контейнеров падает при холодном старте.

Четыре клиента к одному API

Одностраничное приложение, расширение браузера, оболочка на Electron и терминальный интерфейс ходят через один шлюз. Логика прав лежит в одном месте, а не размазана по клиентам.

06

Прогноз спроса и точка заказа

Python · прогноз по истории продаж

Отвечает на вопрос, которого нет в остальных разделах: сколько товара понадобится и когда отправлять заявку, чтобы не встать без него и не заморозить деньги в излишке. По каждой из ста двадцати двух позиций — прогноз, страховой запас, точка заказа и честная ошибка модели.

источник данных обработка что видит человек
Стек Python · собственный расчёт без внешних библиотек · графики своей разметкой
Как устроено

Прогноз объяснимый, а не «чёрный ящик»

Уровень берётся скользящим средним за четыре недели, к нему добавляется тренд и коэффициент дня недели. Каждое число в таблице можно разложить обратно и объяснить поставщику.

Точность считается на том, чего модель не видела

Последние тридцать дней истории при обучении откладываются: прогноз строится по остальным, а потом сравнивается с ними. Ошибка на своих же данных ничего не значит.

Страховой запас от разброса, а не от страха

Считается по отклонению дневного спроса и корню из срока поставки при уровне обслуживания 95%. Ровный спрос требует меньше запаса, скачущий — больше.

Точка заказа вместо календаря

Заявка отправляется не по расписанию, а когда остаток опустился до спроса за срок поставки со страховкой.

Решения и почему так

Простая модель вместо сложной

На дневных продажах с недельной сезонностью скользящее среднее с профилем даёт ошибку около двадцати процентов. Сложная модель выиграет несколько пунктов, но её нельзя объяснить в переписке с поставщиком, а решение о закупке принимает человек.

Ошибка показана рядом с прогнозом

У каждой позиции своя точность: у ровных продаж она в разы лучше, чем у редких. Без этой цифры прогноз выглядит одинаково надёжным везде, а это неправда.

Считается на месте, без сервера

История, прогноз и расчёты вшиваются в страницу при сборке. Открывается двойным щелчком, работает без интернета — как и остальные разделы портфолио.

Рядом с картой, а не отдельно

Прогноз показан вместе с картой страны по кластерам: карта отвечает, где продаётся и где кончается запас, прогноз — сколько понадобится. Карта берётся из дашборда логистики как есть: тот же код и те же данные, просто открытая сразу и без обвязки.

07

Сценарий с повтором, поиск по смыслу и агент

JS · три приёма работы с моделью и сервисами

Три приёма, на которых держится автоматизация с моделью: сценарий, который переживает отказ площадки; поиск, который отвечает на вопрос своими словами; агент, у которого есть список инструментов и правило остановки. Каждый сведён к рабочему экрану и считается прямо в странице.

источник данных обработка что видит человек
Стек Кофе в капсулах Nespresso «PIANO 2», 10 шт. Aurora Coffee JS · косинусная близость · без внешних библиотек
Как устроено

Сценарий: шаг, проверка, повтор

Узлы идут по очереди, у каждого свой результат. Отказ по лимиту не роняет сценарий: он ждёт указанное время и повторяет только упавший шаг, а не всю цепочку.

Поиск: смысл вместо слов

Каждый кусок регламента переведён в набор чисел. Вопрос переводится так же, ответом становится ближайший по направлению вектор — совпадение слов не требуется.

Агент: инструменты и правило остановки

Агент — это модель плюс список доступных действий и условие выхода. Инструменты отмечаются вручную, каждый шаг стоит денег, и итог показывает цену прогона.

Решения и почему так

Считаем в странице, а не на сервере

Экраны должны открываться с диска и без интернета. Векторы и близость считаются на месте: это десятки строк, зато ничего не зависит от сети и ключей.

Повтор только упавшего шага

Перезапуск всей цепочки удваивает нагрузку на площадку и снова упирается в лимит. Повторяется ровно то, что не прошло, с задержкой, которую площадка сама и назвала.

Стоимость видна сразу

Без цены прогона агент выглядит бесплатным. Когда каждый инструмент стоит денег, выбор между лёгкой и крупной моделью становится расчётом, а не вкусом.

Как устроено

Три экрана вместо одного большого

Показатели, а не журнал

Сырые строки журнала ничего не решают. На экран выведено то, по чему принимают решение: что повторялось, у кого кончается квота, какая модель дешевле при той же точности.

Дашборд-центр: тринадцать разделов

Кофе в капсулах Nespresso «PIANO 2», 10 шт. Aurora Coffee JS · Apps Script как бэкенд

Инструментарий отдела, собранный в одно приложение: витрина, фиксация заказов, реклама, остатки, два калькулятора юнит-экономики, разбор заказа на сырьё и база регламентов.

источник данных обработка что видит человек
Стек Кофе в капсулах Nespresso «PIANO 2», 10 шт. Aurora Coffee JS без фреймворков · Google Apps Script · Google Sheets как хранилище · SheetJS · Electron · Android WebView · PWA
Как устроено

Один шлюз на все вызовы

Разделы не ходят в площадки напрямую: они заворачивают адрес, метод и тело в конверт и отдают его шлюзу. Ключи живут на стороне шлюза и в браузер не попадают.

Ответ бывает и JSONP

Часть разделов запрашивает данные тегом script, а не fetch. Такому вызову нужен ответ-вызов функции: иначе браузер разбирает JSON как код и падает на первом же двоеточии.

Справочник один на всех

Коды 1С, штрихкоды, формат и капсульность лежат в одном справочнике. Если у калькулятора справочник свой, себестоимость перестаёт сходиться с позициями заказа.

Решения и почему так

Роль выбирается один раз

Выбранная роль применяется во всех разделах и решает, что человек видит. Приложение ведёт аудит: кто заходил, куда и надолго ли — чтобы видеть, чем реально пользуются.

Одна кодовая база на три упаковки

Веб, программа для компьютера и приложение для телефона собираются из одних и тех же файлов. Правка в разделе доезжает всюду за один прогон синхронизации.

Разделы приложения по отдельности

у каждого свой источник и свой формат

Разделы писались под разные источники: где-то отвечает кабинет площадки, где-то служебный скрипт таблицы, где-то файл, который человек перетаскивает на страницу, а где-то данных нет вовсе — раздел считает по снимкам соседей. Ниже каждый по отдельности.

P&L · учётная система

index.html
учётная система, OData→разбор проводок→прибыль и рентабельность
Откуда данные

Счета доходов и расходов выгружаются напрямую из учётной системы по OData через ретранслятор: запрос уходит с логином базы, ответ приходит разобранным по месяцам.

Формат обмена

OData (XML/JSON) · период задаётся датами

Что считает

Выручка без НДС, расходы по статьям, операционная прибыль, рентабельность; два графика — доходы против расходов и структура расходов.

Решение

Ретранслятор вместо прямого запроса из браузера: учётная система не отдаёт данные на сторонний адрес, а логин не должен лежать в странице.

Разбор заказа на сырьё

KapsDash.html
файл сборки заказа→справочник + нормы→потребность и себестоимость
Откуда данные

Файл сборки перетаскивается на страницу. Нормы и цены берутся из общего справочника, который загружается один раз в разделе данных.

Формат обмена

Что считает

Заказ раскладывается на капсулы, упаковку, фольгу, плёнку, стаканчики и ароматизаторы; считается количество каждого и себестоимость всего заказа.

Решение

Расчёт идёт в браузере, файл никуда не уходит: заказ — коммерческая информация, ей незачем путешествовать по сети.

Производство

foxdash.html
рабочий лист таблицы→этапы и роли→план и что горит
Откуда данные

Заказы и их состояние лежат в таблице, куда пишут со смены; страница читает их через служебный скрипт таблицы.

Формат обмена

Google Apps Script (JSON) · роль хранится в браузере

Что считает

Заказы по этапам: фасовка, обработка, контроль, сборка. Разбивка по площадкам, ABC-группы, приоритеты, счётчики к выполнению.

Решение

Экран зависит от роли: у оператора свой список, у руководителя — сводка. Одна страница вместо четырёх похожих.

Остатки по площадкам

SOWY.html
шесть площадок→сведение к одному виду→что везти и куда
Откуда данные

Шесть источников с разными правилами: две площадки отдают JSON по ключу, одна требует конверт с описанием запроса, ещё одна отвечает постранично, отчёт шестой приходит текстом из таблицы.

Формат обмена

REST (JSON) · конверт с телом запроса · CSV из Google-листа

Что считает

Остатки и продажи по товарам и складам, запас хода в днях, что срочно везти и что залежалось. Отдельными окнами: формирование поставок с расчётом до целевого запаса и разбивкой по кластерам; карта продаж по регионам и округам с топом и списком «куда везти в первую очередь»; лента новостей площадок с пометкой того, что меняет расчёт; сводка для руководителя и разбор рынка конкурентов по категориям.

Решение

Скорость продаж раскладывается по складам пропорционально остатку — иначе поставка считается только там, где площадка отдала разбивку сама. Карта нарисована своей разметкой, а не внешней подложкой: раздел открывают с диска и без интернета.

Реклама и ставки

кабинеты рекламы→сведение кампаний→ДРР и что проверить
Откуда данные

Три рекламных кабинета: у каждого свой способ входа и своя форма отчёта. Выручка для расчёта доли берётся из отчёта о продажах, а не из заказов.

Формат обмена

REST (JSON) с обновляемым ключом доступа

Что считает

Расход, заказы, ДРР, CTR, корзины и доля рекламы в выручке; сигналы «что проверить»: ставки, карточка, остатки, цена, доставка.

Решение

Доля рекламы считается от продаж, а не от заказов: на заказах она уходила в сотни процентов и показатель терял смысл.

Фиксация заказов

OMDash.html
заявки из таблицы→календарь и статусы→отгрузки и письма
Откуда данные

Заявки на отгрузку и записи о поставках лежат в таблице; страница читает и меняет их через служебный скрипт — создание, удаление, отправка письма.

Формат обмена

Google Apps Script (JSON), запись и чтение

Что считает

Календарь на месяц: поставки и заявки с цветом по состоянию, фильтры, счётчики по дням, письмо контрагенту в один клик.

Решение

Состояние заявки определяется по факту отгрузки, а не по галочке: иначе закрытыми считаются заявки, которые ещё едут.

Сводка руководителя

снимки других разделов→свёртка и прогноз→пять блоков решений
Откуда данные

Единственный раздел, который никуда не ходит: он берёт снимки, оставленные другими разделами при загрузке, и считает по ним.

Формат обмена

Память браузера (снимки разделов)

Что считает

Выручка, маржа, капитал на остатке, оборачиваемость, дефицит и затоваривание; прогноз — тренд по последним дням, помечен как ориентир, а не пророчество.

Решение

Себестоимость подставляется по всем кодам товара сразу — штрихкод, код учётной системы, внутренний код площадки. Иначе маржа выходит стопроцентной.

Стоимость логистики и хранения по кластерам, объём и вес поставки, локализация, сравнение вариантов отправки.

Значения тарифов вынесены отдельно от расчёта: сетка меняется несколько раз в год, и правка не должна трогать формулы.

Откуда данные

Один справочник на все разделы. Пока он был у каждого свой, один и тот же товар считался по разной себестоимости.

Решение

Сборка заказов

выгрузки заказов площадок→разбор, сведение, короба→задание складу и общая сборка
Откуда данные

На вход идут выгрузки заказов из разных кабинетов — у каждой площадки своя форма файла, свои заголовки и своя нумерация. Плюс собственная база товаров с кратностью короба и принадлежностью юрлицу.

Формат обмена

Excel и CSV разных форматов · собственная база с индексами · запись в Google-лист · выгрузка ZIP

Что считает

Площадка определяется по имени файла и по содержимому — заголовки в выгрузках плавают, поэтому строка заголовков ищется перебором, а файлы без заголовков разбираются по позициям колонок. Строки разных файлов сводятся по коду учётной системы, количество приводится к кратности короба своей площадки, позиции сортируются по приоритету. Дальше собирается общая сборка на смену, раскладка по коробам и паллетам и выгрузка задания для склада архивом.

Решение

Формат входного файла не задан жёстко: площадки меняют выгрузки без предупреждения. Раздел узнаёт формат сам и говорит, если файл не похож ни на один известный, — это дешевле, чем ломаться на каждой правке площадки.

Как собираются приложения

одна кодовая база — три упаковки

Веб-версия, программа для компьютера и приложение для телефона собираются из одного исходника. Ни одна из сборок не тянет страницы из сети: файлы лежат внутри приложения, поэтому оно работает и без интернета.

Программа для компьютераElectronТот же сайт запускается внутри окна Electron: main.js создаёт окно и открывает локальный index. Сборка — electron-builder, на выходе установщик NSIS для Windows. Приложение работает без интернета.
